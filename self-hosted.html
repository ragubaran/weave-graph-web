Packaging Tier

1. Custom Mode Architecture

--features custom

While standard Single Mode (individual developers) and Multiple Mode (local multi-repo links) run entirely offline without coordination, Custom Mode activates the enterprise tier for organizations that require centralized graph synchronization, team access controls, and automated compliance gates.

Feature Bundle
Bundles team, hub, rbac, otel, policy-lint, fts, and vector.
Zero Cloud Leaks
Core Invariant 1 preserved: all parsers, queries, and RBAC guards execute 100% locally with zero third-party cloud egress.
Feature Isolation
Zero idle RSS delta: optional features are decoupled behind conditional compilation, keeping inactive memory footprint at 0 MB.

Compiling & Installing Custom Mode

# Build from source with the complete custom enterprise feature bundle
cargo install --locked --git https://github.com/ragubaran/weave-graph weave-graph-cli --features custom

# Initialize a repository with custom enterprise configuration
weave init --mode custom

# Check active features and compiled subsystems
weave status
Prebuilt Binary: Enterprise deployments can distribute the pre-compiled weave-custom binary (~41.6 MB stripped release) containing all enterprise modules, or weave (~13.8 MB core build) for standard developer workstations.
Access Control

2. Query-Layer RBAC & SCIM 2.0 Directory Sync

feature: rbac
Core Invariant Rule §1.7: RBAC is enforced at the query and storage layer (weave_graph_core::rbac::RbacGuard), never export-only. When a restricted subject queries the graph, masked internal nodes and edges are filtered at traversal time. CLI, weave report, exports, and MCP all inherit the exact same security guard.

1. User & Role Configuration (.weave/config.toml)

Map identities to roles directly in configuration. Internal symbols with private/internal visibility rules are automatically hidden from external or contractor roles: 

[rbac]
enabled = true

[rbac.users]
alice = ["admin", "core-team"]
bob = ["internal-dev"]
external-contractor = ["external"]

[rbac.roles]
# External roles only see public API boundaries and exported interfaces
external = { allow_internal_symbols = false, allow_unexported_contracts = false }
core-team = { allow_internal_symbols = true, allow_unexported_contracts = true }

2. Executing Queries with Subject Identity

# Internal engineer query: returns complete call graph
weave query "callers(AuthService.validateSecret)" --as alice

# Contractor query: internal helpers and sensitive AST nodes are automatically masked
weave query "callers(AuthService.validateSecret)" --as external-contractor

# Run MCP server bound to a specific identity context
weave serve --mcp --as external-contractor

3. SCIM 2.0 Identity Directory Server (weave rbac serve-scim)

Integrate with corporate enterprise IdPs (Okta, Microsoft Entra / Azure AD, Google Workspace) without outbound network requests. IdPs push provisioning events directly to Weave's loopback SCIM endpoint, which snapshots state to .weave/rbac-directory.toml: 

# Launch the loopback-only SCIM 2.0 provisioning daemon on port 8080
weave rbac serve-scim --port 8080

# The server provides standard SCIM endpoints:
#   GET  /Users        - Enumerate provisioned users
#   GET  /Users/{id}   - Fetch user roles and metadata
#   POST /Users        - Provision new user identity
#   DELETE /Users/{id} - Deprovision user (revokes query access on next sync)
Centralized Synchronization

3. Graph Hub & Standalone Registry

feature: hub

The Graph Hub provides centralized snapshot storage and delta distribution across CI runners and developer pods. Instead of reindexing large multi-million-line monorepos from scratch, developers pull pre-computed graph snapshots in milliseconds.

1. Deploying the Standalone weave-registry Server

Deploy the dedicated registry daemon on a shared internal server or container. It handles disk spool queues, sequential per-repo commits, and backpressure rate limits: 

# Run weave-registry with calibrated merge-rate limits
weave-registry   --bind 0.0.0.0:8080   --data-dir /var/weave-hub/data   --max-queue-depth-per-repo 50   --max-pushes-per-minute-per-repo 10

2. Client Configuration & CI Automation

Configure repositories to synchronize with your internal hub: 

# Point local repo to the internal hub
weave config set hub.url "http://hub.internal.corp:8080"

# Hydrate graph snapshot for current commit (with fallback to latest default-branch snapshot)
weave sync pull --fallback-latest

# In CI post-merge pipeline: publish freshly indexed snapshot
weave sync push
Snapshot Provenance & Tamper Verification (hub-provenance)
Enable cryptographic snapshot signing via --features hub-provenance. Every published snapshot payload is accompanied by an X-Weave-Signature header generated with HMAC-SHA256 or external hardware security modules (Lodestone Nexus). Corrupted or tampered snapshots are rejected before hydration.
Production Telemetry

4. OpenTelemetry Traces & Latency Profiling

feature: otel

Bridge runtime observability with static code intelligence. The otel feature imports OpenTelemetry (OTLP JSON) spans directly into the graph database, matching live execution timings with AST function symbols.

1. Ingesting OTLP JSON Traces

# Ingest exported OpenTelemetry traces from your APM or Jaeger/Tempo collector
weave traces import telemetry-export.json --path .

2. Querying Live Percentile Latencies

Query nearest-rank p50, p95, p99 latencies, call counts, and error rates directly through the graph query engine: 

# Query live latency statistics for a critical function
weave query "latency(PaymentService.executeCharge)"

# Output:
# Symbol: PaymentService.executeCharge
# Spans: 14,280 | Errors: 12 (0.08%)
# Latency: p50=12.4ms | p95=48.1ms | p99=114.6ms | Max=340.2ms
RBAC Guard Integration: Trace queries resolve symbols against the caller's RBAC guard first. If a developer lacks permission to inspect a sensitive payment microservice, the query fails symbol resolution, preventing unauthorized telemetry probing.
Governance & CI Gate

5. Architectural Policy Linter & Drift Detection

feature: policy-lint

Prevent architectural erosion and enforce layered boundaries in CI. Declare allowed and prohibited cross-module call patterns in .weave/policy.yaml and block violating pull requests automatically.

1. Defining Boundary Policies (.weave/policy.yaml)

# Architectural layer boundaries
rules:
  # Presentation tier must never bypass domain layer to call database directly
  - disallow:
      from: "crates/frontend/**"
      to: "crates/database/**"

  # Core models must never depend on external network adapters
  - disallow:
      from: "crates/core/**"
      to: "crates/network/**"

  # Payment modules must explicitly route through encryption vault
  - require:
      from: "crates/payment/**"
      to: "crates/crypto/vault/**"

2. Executing Policy Checks in CI

# Evaluate boundary rules: exits 0 on pass, non-zero with violation diff on failure
weave policy lint

# Detect architectural drift: circular dependencies (Tarjan SCC) and orphaned files
weave policy drift
Offline AI Intelligence

6. Local SLM Intent Routing & Document Mining

feature: slm

The slm feature provides an on-premises natural language terminal interface for developers (weave ask), converting conversational questions into exact graph traversals with zero cloud exposure.

1. Managing Quantized On-Device GGUF Models

# Download and verify checksum of compact on-device models
weave slm pull qwen2.5-coder-0.5b --sha256 <digest>

# Inspect local model cache and quantization formats
weave slm list

# Run diagnostic verification suite for tool-selection and grounding accuracy
weave slm doctor

2. Natural Language Queries & Rule Mining

# Terminal question -> automatically grounded against AST symbol table -> runs callers()
weave ask "Which services depend on the authentication token validation?"

# Scan ADRs and markdown documentation for architectural invariants ("must", "should never")
weave slm review-rules --confirm

# Synthesize commit changelog correlated with graph blast radius
weave journal --since main

7. Schema Registry & Virtual Federation

feature: federation

For enterprises organized into microservices or distributed multi-repo workspaces, Weave Graph links distinct repositories into a unified composite graph without requiring a centralized monolithic database. 

# Link sibling microservice repositories into a composite graph
weave link ../auth-service ../payment-gateway ../notification-service

# Verify public API contract signatures across repository boundaries in CI
weave check-contracts

# Generate multi-repo visual architecture report with Louvain community clustering
weave report-federated ../auth-service ../payment-gateway
Infrastructure

8. Storage Vaults & Shared Read-Only Network Mounts

storage topology

In enterprise clusters with ephemeral containers or network filesystems (NFS, SMB, EFS), SQLite WAL mode can fail due to lack of shared memory (/dev/shm). Weave Graph solves this with dedicated vault paths and non-WAL read-only snapshot exports:

1. Central Storage Vault Configuration

# Option A: Central storage directory for a specific repository
weave config set storage.home /var/weave-vault/repo-payments

# Option B: Global environment variable for developer workstations and CI agents
export WEAVE_HOME=/var/weave-vault

2. Shared Network Snapshot Export (Non-WAL Mode)

Export pre-indexed databases into clean non-WAL snapshots mounted read-only across thousands of worker containers: 

# Export snapshot using standard rollback journal (NFS-compatible, no shared memory required)
weave export --format sqlite --readonly /mnt/nfs/snapshots/graph.db

# Querying nodes automatically detects read-only mounts and applies PRAGMA query_only = ON
weave query "impact(OrderProcessor)" --db /mnt/nfs/snapshots/graph.db
