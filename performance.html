CSR Memory Optimization & SLO Target Validation

✅ Target SLO Met (≤ 8 Bytes/Edge)
❌ Historical State (Missed)

Measured at 12 bytes/edge (24 B/edge bidirectional). Caused by storing an unused 8-byte f64 edge weight (Csr<(), f64, ...>) alongside the 4-byte u32 target index.

⚡ Optimizations Applied
  • Dropped Unused Weight: Replaced Csr<(), f64, ...> with Csr<(), (), ...> in csr.rs (eliminated 8B overhead).
  • Lazy Reverse CSR: Converted reverse_csr to construct lazily via OnceLock on first call to callers_within.
✅ Current Verified State

Forward path (common case): ~4.0 bytes/edge (~12.0 B/node).
Bidirectional path: ~8.0 bytes/edge (~24.0 B/node) when callers_within is invoked.
Status: Comfortably under the ≤8 bytes/edge SLO target.

Transparent Engineering Notes & Root Causes

Weave Graph does not gloss over architectural compromises. When an empirical measurement diverges or balances packaging breadth against resource constraints, the engineering cause is documented openly:

Note 1: AST Parser Speed

The >25 MB/s target originally modeled raw Tree-sitter C lexing throughput. In practice, parse_file executes full wiring-card generation, scope resolution, moniker string internments, and structural call edge creation, bounding throughput to 3.08–4.77 MiB/s per core.

Note 2: CSR Memory per Edge Optimization

Initially measured at 12 bytes/edge (24 B/edge bidirectional) which missed the ≤8 B/edge Target SLO due to storing an unused 8-byte f64 edge weight (Csr<(), f64, ...>). By dropping the weight overhead (Csr<(), (), ...> in csr.rs) and constructing reverse CSR matrices lazily via OnceLock on first call to callers_within, memory footprint was reduced to ~4.0 bytes/edge forward (and ~8.0 bytes/edge bidirectional), cleanly achieving the ≤8 bytes/edge Target SLO.

Feature Flag Budget

Optional features are isolated behind Cargo feature flags: enabling a feature never changes core behavior or measurably degrades default query latency or idle RSS for users who don't enable it.
